*sshole: дыра в OpenSSH впускает на серверы Alpine без пароля — достаточно одного подключения

06.11.2026 · по материалам первоисточника
5 ноября проект Alpine Linux выпустил экстренный бюллетень: уязвимость с именем *sshole позволяет войти по SSH на аккаунты «без пароля», не зная никакого пароля — с одного подключения, без повторов. Нужны длинный пароль-заглушка и обычная конфигурация по умолчанию. Уже доступны OpenSSH 10.6p2 и исправленные пакеты для всех веток Alpine, включая снятые с поддержки.

Что произошло

5 ноября Alpine Linux опубликовал уведомление об обходе парольной аутентификации в openssh-server. Атакующий, которому доступен SSH-порт, входит на машину без знания пароля: в бюллетене это сформулировано так — «одно соединение, срабатывает всегда, повторы не нужны». Уязвимость нашёл исследователь Эзгюн Кюльтекин (группа Wakefield) и дал ей говорящее имя *sshole. В тот же день проект OpenSSH выпустил исправленную версию 10.6p2, а Alpine собрал патченные пакеты для всех веток с 3.16 по 3.24 — включая релизы, уже снятые с поддержки.

Странные условия срабатывания

Наложиться должны три факта: система на libc musl (это фирменная лёгкая библиотека Alpine) и пакете OpenSSH, собранном без PAM; включённая парольная аутентификация — в OpenSSH это настройка по умолчанию; и наличие аккаунта со звёздочкой `*` в поле пароля — так нормально живут аккаунты, которые пускают только по ключу (с 3.16 так живёт и root в базовом образе). Второе условие: хотя бы одна учётная запись с обычным хэшем `$5$`/`$6$` — у неё «одалчивается» соль. После этого атакующему достаточно отправить пароль длиннее 256 байт (диапазон 257–1024). Root по умолчанию прикрыт настройкой PermitRootLogin prohibit-password, но если у скомпрометированного пользователя есть права doas или sudo — root в одном шаге.

Почему так вышло

Механика из бюллетеня: без PAM sshd проверяет пароль функцией crypt() и сравнивает результат с записанным полем. Если сохранённое поле слишком короткое, чтобы содержать соль, sshd берёт соль чужого аккаунта. А musl-версия crypt() при ключе длиннее 256 байт возвращает строку `*` как индикатор ошибки — ровно то и записано в поле пароля у аккаунтов без пароля. «Хэш» совпадает, вход разрешён. Проект OpenSSH считает, что корень проблемы лежит вне sshd, разработчики musl отвечают, что библиотека ни при чём — её просто некорректно вызывали. На момент публикации бюллетеня CVE не был присвоен; позже OX Security завела CVE-2026-123158 с оценкой 8,1 балла.

Почему это серьёзно

Базовый образ Alpine на Docker Hub перевалил за миллиард скачиваний; дистрибутив годами живёт в роутерах, смарт-телевизорах и промышленных контроллерах, которые вообще не обновляются. По данным Detectify, Shodan показывает около 22 миллионов систем с открытым 22-м портом: под все условия уязвимости подходит лишь часть, но проверить каждую — дело минут. Автор находки также назвал затронутыми OpenWrt (там по умолчанию стоит Dropbear, а не OpenSSH), buildroot и Yocto — последнее пока не подтверждено.

Что делать прямо сейчас

Правильный ответ официального Alpine: `apk upgrade -U -a` и обязательный перезапуск демона (`rc-service sshd restart`) — обновление пакета само по себе работающий sshd не заменяет. Обновиться нельзя — выключить вход по паролю (`PasswordAuthentication no`), предварительно проверив, что вход по ключу работает. Проверить следы взлома можно в /var/log/messages по строкам `Accepted password` для аккаунтов, у которых пароля нет вовсе; если такой вход не исключить — считать машину скомпрометированной и проверять doas, новых пользователей и authorized_keys.
